# Correlation semantics

The implemented rule is `manual-cve-review/v1`: a user selects a CVE for a particular installation, the public CVE JSON 5 record is retrieved, and a technology-review relationship is persisted. This is **not product matching**. Names, CPEs/PURLs, or the CVE selection itself do not prove applicability. Unknown versions remain unknown. The category is technological relevance, automated applicability is unknown, confidence is unassessed, and priority is human review with an explanation that includes asset criticality. No CVSS-to-compromise inference or exploitation claim is made.

`SourceRecord` preserves raw evidence and ingestion time. `Finding` stores source reference, installation, versioned rule, evaluation time, optional observation time (unset rather than invented), and the original reasoning. Raw evidence is available through an authorization-filtered JSON endpoint. Repeated lookups upsert the record and reuse the finding; existing workflow and analyst overrides survive. There are no finding notifications yet, so repeated imports cannot send alerts. The latest retrieved source payload replaces the projection; immutable source-version history is planned.

Workflow status and analyst applicability are separate. Reviewers record a reason and previous/new values in history. Confirming workflow alone does not change automated applicability. These assessments never establish compromise. No automatic software version comparison is implemented; affectedness needs structured vendor applicability, fixes/backports/configuration and source-specific matching in milestone 2.

Future categories must remain distinct: direct infrastructure reference, potential applicability, exploitation of a relevant vulnerability, technological relevance, observed external exposure, inventory discrepancy. Public exploit availability, exploitation elsewhere, known-exploited catalogs, and exploitation of this organization require different evidence. A CVE mention in MISP is not exploitation; a scan tag is not affectedness; copied reports are not independent evidence.

Scope matching uses DNS label boundaries, IPv4/IPv6 arithmetic and historical intervals `[valid_from, valid_until)`. Only verified claims participate. Private/non-global addresses require the same organization and network context; overlapping public claims are supported and not exclusive. Claim matching functions are tested but not yet wired into an automatic correlation pipeline.

Stale inventory, absent sources, unknown versions, and missing matches must remain visible. Last-known source timestamps appear on inventory pages. No matching result means no matching evidence within the implemented coverage, never safety. Freshness thresholds, evidence visibility policies, origin deduplication, and a generalized observation/relationship model remain planned.
