# Company configuration and resumable setup

Open **Company configuration & setup** from the Infrastructure overview or your organization's workspace. Company administrators and platform administrators can configure the organization. Inventory editors/readers and CIRCL-only analyst access do not grant access to confidential monitoring preferences.

## Registration and approval

Registration asks for the organization, optional address, responsible person, emergency telephone, personal email, optional team mailbox and existing participation commitments. IPs/networks/domains are collected later instead of making registration depend on a complete infrastructure list. Optional public PGP material and a PEM S/MIME certificate can be pasted during registration; they are copied to the private company after personal mailbox confirmation. Existing submitted declarations and registrations are retained.

The guided wizard opens after CIRCL approval and while sharing remains allowed. The approval email links to it. Individual configuration sections and existing company editors remain available in the private area before approval and after sharing revocation. No forced redirect prevents using the application normally.

## Sections

1. **IPs, networks & domains:** bounded bulk entry of active self-declared IPs, strict CIDRs/ranges and DNS names in one network context. Valid automatic saves update declarations. Removing a line withdraws that declaration with retained history; it never verifies authority. Verified/disputed/expired claims stay in the individual editors. For multiple contexts or more than 100 existing declarations, use those editors; the bulk editor refuses to merge/drop them.
2. **Hardware & software:** registered manual-source companies can automatically save a named asset and its first software/OS/version record. Repeated saves update the same records; **Save & add another asset** starts another entry. Blank versions remain unknown. Individual asset/software editors add further details or installations. Existing NetBox/development sources use their established entry/import tools; wizard autosaves never create an upstream write. Remaining-work notes are resumable.
3. **AIL preparation:** optional keywords, separately typed Honeytokens and an optional different-team notification email. These are confidential company-admin preferences. **Download AIL YARA configuration** is an explicit local POST download of saved indicators. Import its contents as custom YARA tracking rules in your trusted AIL installation. Keyword strings match substrings with ASCII case-insensitivity; Honeytokens preserve case. UTF-8 matching is byte-based. Review source filters, access and recipient settings in AIL before enabling tracking. The routing mailbox is not verified or automatically subscribed. There is no AIL API connection, data synchronization, automated finding import or automatic notification; analysts review false positives and decide how to contact the company through the existing Bearings/AIL workflows.
4. **Contacts & secure communication:** company address, optional public PGP/S/MIME material and links to technical/security/DPO contacts, reminders and escalation. Private keys/PKCS#12 are refused. PGP armor/public-packet structure and PEM X.509 syntax are checked; certificate trust, expiry, mailbox binding, key ownership and encryption usability are not asserted. No outgoing mail becomes encrypted merely by saving a public key. The current public material is available on the ordinary company page to currently permitted company members/CIRCL; confidential AIL indicators are not included there.

The last section saved in the wizard or an individual configuration page is the resume point. Every section can be opened directly, in any order. Existing company, scope, asset, software, contact and address editors remain usable independently.

## Saving and progress

Fields save automatically after a short pause or field change. **Save now** and ordinary HTML form submission remain available without JavaScript. Valid saves update current company data; invalid non-key drafts are retained within field size limits for correction. Rejected key material and oversized field values are never persisted as drafts. The save status and validation errors distinguish these cases. Navigation waits for pending saves; an unsaved-change warning covers failed requests or rejected material. A lost response can require reconciliation even if the server committed the first save.

Company administrators share server-side drafts across sessions/devices. Section revisions and a current-data digest detect another tab/admin or a supported individual editor changing that section: HTTP 409 leaves your text on screen instead of overwriting newer data. Copy/reconcile it before reloading. There is no browser local-storage copy of Honeytokens or key material.

Choose **Mark section reviewed** after checking a section. Scope requires a current declaration; inventory requires an active asset with a software record; contacts require an email/emergency telephone contact. AIL can be explicitly left unused. Later configuration edits reset that section's review; removing required inventory also reduces progress. The bar reaches 100% when all four sections have been reviewed. It measures setup participation, not inventory completeness, verified authority, email reachability, patch status or security. Mandatory periodic data reviews remain separate. Canonical configuration/key changes invalidate a previously prepared signed data-review snapshot.

## Operations and privacy

Migration 0034 adds blank-compatible registration fields and organization-owned configuration/section tables; there is no retroactive consent or generated private key. Default local service mail remains unchanged. Views are authenticated, current-company scoped, private/no-store and CSRF protected; guided access also rechecks current approval on every save. Audit events record section/action metadata, never monitoring values or key bodies. AIL downloads contain sensitive indicators and must be handled by trusted operators. They do not contain the optional routing email and do not configure AIL mail/webhooks.

AIL custom-YARA support was checked against the upstream [`hunters.py`](https://github.com/ail-project/ail-framework/blob/master/var/www/blueprints/hunters.py) and [`Tracker.py`](https://github.com/ail-project/ail-framework/blob/master/bin/lib/Tracker.py) source on 2026-11-18. Generated rules are syntax/match tested locally; an actual import into the operator's deployed AIL version remains a separate acceptance step. No live AIL instance was contacted during development.

The contacts section links to **SSO & access** for the approved registered responsible person. [Company SSO](company-sso.md) explains explicit identity linking and separately provisioned native NetBox permissions; completing the wizard never grants application roles automatically.
