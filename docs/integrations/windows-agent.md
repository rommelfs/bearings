# Windows machine inventory observations

Implemented reference increment, 24 November 2026. See [client setup and commands](../../clients/windows/README.md). This extends the existing [authenticated Linux observation receiver](linux-agent.md); its organization/source ownership, current authorization, expiry, revocation, replay and analyst-decision protections remain in force. No production rollout or operational data publication is performed.

## Collection and ownership

The Windows Python client reads `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion` for reported product name, edition, display release, build and UBR. Build plus UBR is the observed OS version. ProductName is retained as reported; it is not normalized into a Windows 10/11 marketing identity or a Microsoft security product ID. Reboot requirement and effective remediation remain unknown.

Additional software comes from named entries under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` in both explicit Windows registry views. View 32/64 describes the registration location, not verified binary architecture: component architecture is `all`. All named registrations, including entries hidden from Add/Remove Programs, are eligible; publisher/version may be unknown. Empty names are skipped. No install/uninstall command, executable path, username, user SID, product key or serial is collected. Per-user/Store/portable/WSL and KB/update inventories remain future capabilities.

The implementation follows Microsoft's documented [uninstall registry metadata](https://learn.microsoft.com/en-us/windows/win32/msi/uninstall-registry-key). Registration is self-reported evidence, not proof of complete software coverage, trusted publisher or vulnerability applicability. Windows DPAPI uses [user-scoped CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) and [CryptUnprotectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptunprotectdata) to retain confidential state; Windows administrators and the reporting account remain trusted.

A `windows-machine` report uses the existing `bearings.agent.v1` envelope with OS id `windows`, exactly one OS component, manager `win-reg`, no services/application probes and bounded `windows` evidence. OS component identity is `win-reg:os:all`. Program identity hashes the case-folded complete uninstall key and registry view; two views/installations are never merged just because names match. Receiver recomputes identities and validates paths, evidence, OS build consistency, counts and text bounds. Missing DisplayVersion is retained as an empty unknown version, never guessed.

Automatically inventoried registrations become separate installation records when the device's existing automatic-software policy allows it; OS receives the operating-system flag. Generic registration identifiers deliberately assert no vendor/CPE mapping. Existing manual software is not adopted by name. Subsequent reports own only their assigned version field. A product-name change or disagreement between two known publishers under a bound registry identity stops publication for explicit ownership review instead of silently retargeting an installation. Human assessments, build/edition ownership and evidence history remain separate. Reported Windows edition/release are retained in observation evidence, not adopted into manually maintained installation fields. Automatic Microsoft CVE/KB applicability is explicitly unavailable; no clean security result is inferred.

## Authorization and failure semantics

An organization administrator/platform superuser approves the public key for an existing visible asset, then the client redeems the key-bound, one-use, expiring code. CIRCL analyst status alone cannot enroll a device. The Windows reference does not yet implement new-host registration, fleet bootstrap, renewal or authoritative NetBox reconciliation. Existing read-only NetBox assets can receive observations; reporting does not grant upstream write permission. Explicit operator export policies remain a separate existing workflow, subject to their own write/capability checks.

No remote commands, installer operations, scans or arbitrary destinations. HTTPS certificate trust is verified, redirects refused and request/response sizes and socket timeouts bounded. Enrollment retry preserves the request identity; report retry preserves exact signed body bytes, with a fresh transport signature. Public keys are printed; private keys/codes/raw transport exceptions are not logged.

“Complete” covers only successful reading of the declared **machine registry + OS** scope. A missing uninstall root is an empty scope. Access errors, detected concurrent edits or disappearance of an enumerated key, malformed/oversized fields, missing OS build metadata or count/body limits abort collection; no partial complete snapshot is transmitted. Delivery/admission failure retains pending bytes and last-known server inventory. Missing registrations from a later successful complete snapshot are flagged as not observed; they are never deleted and do not resolve findings. Unknown versions remain unknown even if a previous report had a version. Registry reads span multiple keys and can observe changes between reads. Failed collection does not refresh coverage timestamps.

## Validation and rollout boundary

Migration **0073** retains Windows component evidence; apply it before restarting web/worker. No new Python dependency or lock update. Synthetic tests exercise registry views, Unicode/unknown versions, real signature admission, automatic OS/software projection, changes/missing retention, revocation, schema refusal, enrollment retry, explicit CA recovery, exact receipts, offline sampling and durable outbox behavior. A proposed native Windows CI job in [windows-ci.patch](../../clients/windows/windows-ci.patch) runs DPAPI tamper detection, state persistence/corruption refusal, concurrent locking and actual local registry collection, without printing/uploading inventory. That patch is supplied, not applied or executed: the current GitHub OAuth access lacks workflow permission. Apply through a workflow-authorized operator before relying on Windows CI.

Local native Windows/Windows Task Scheduler, endpoint ACL/account/profile behavior, independent Windows 11/Server/ARM64 installations and real Windows-to-HTTPS end-to-end acceptance remain **unvalidated** until run on those targets. Signed executable packaging, a reviewed installer/service and centralized Windows downloads remain planned. This is a reviewable first reference, not a fleet deployment acceptance claim.
