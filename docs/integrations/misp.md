# MISP: customer permissions and separate CIRCL investigation

Status: implemented bounded read/cache pilot with **optional customer-owned MISP connections**. The proposed server is `https://misppriv.circl.lu`; it has not been authenticated/validated live here. No real key was provided or used. A universal CIRCL analyst key cannot stand in for a customer's MISP permissions.

## Customer setup

1. A platform administrator approves the MISP destination under **Bearings administration → MISP servers** (`/admin/portal/mispserver/`). Migration 0043 creates a disabled CIRCL MISP entry; approving it makes the URL selectable, without contacting MISP or creating any credential. Saved endpoint URLs cannot be repointed; create a new catalog entry instead. Private destinations/proxy-DNS allowlists remain explicit operator settings.
2. The customer signs in with their **individual Bearings account**, opens **My MISP → My personal MISP connection**, selects their own company and the approved server, and enters **their own personal read-only MISP key**. The URL is shown; arbitrary customer-supplied destinations are not accepted.
3. Setup reads only `GET /users/view/me` using that key, pins the returned native MISP user ID, and encrypts the key. It neither imports CIRCL data nor grants company roles. A complete background snapshot using this same key is required before events appear. Native-ID entry and CLI access are unnecessary for customers.
4. **My MISP** shows only that user's available personal caches. Key replacement must retain the native MISP identity while connected. Disconnect removes the stored encrypted key and hides the cache. Connecting another native account afterward creates a new connection; old cached data is never reassigned.

MISP is optional. Companies without a MISP account/key can continue to use inventory, public vulnerability matching and separately reviewed notifications. A company administrator or colleague does not inherit another member's key/cache. Current membership in the connection's company is required, even for a user who belongs to several companies. Local infrastructure research stays within that connection's company; choosing a company does not assert that every MISP event describes that company or prove infrastructure ownership.

The native MISP API response under the customer's key determines event and attribute visibility. Bearings does not substitute a CIRCL/operator key on failure, missing credentials, decryption errors or empty results. Customer connections cannot use operator environment-key mode. The same UUID can have a narrower attribute set in a customer cache than in a CIRCL cache; they remain different records. Raw content, titles, counts and derived research never cross those caches. Native `Org`/`Orgc`, company UUID references and email matches do not grant access.

## Credentials and lifecycle

Customer keys are write-only UI inputs, encrypted using Fernet with a purpose/owner/company/connection-bound key derived from the private Django application secret. They are never shown again or returned in HTML, query strings or audit data. The public development fallback/short application secret cannot store a key; the bundled stack's generated private secret supports this automatically. Keep `DJANGO_SECRET_KEY` outside Git. App-secret rotation requires retaining the old value in Django `SECRET_KEY_FALLBACKS` until credentials have been re-encrypted/reconnected; losing all applicable encryption secrets requires reconnection, never a CIRCL fallback. This protects stored API keys, not entire databases/backups.

Setup has a per-user ten-attempt/ten-minute limit and CSRF protection. Native user responses can include auth keys: only the ID is consumed, and secret-bearing local variables/POST values are excluded from production exception reports. Source ownership/native ID/endpoint/credential nonce cannot be repointed after a personal key has been stored. A disabled endpoint, changed policy, lost membership, inactive owner or disconnected key suspends access. A former company member can still remove their own stored key, without access to company details or cached events. Disconnect does not revoke the native MISP key or erase old backups; users manage native key revocation separately. Cached payload retention and database/backup protection remain operator responsibilities.

## Read/cache contract and permission freshness

The pinned [MISP 2.5 OpenAPI](https://github.com/MISP/MISP/blob/7dce1ef58bc16f0249ea4b53b2a29585645145a3/app/webroot/doc/openapi.yaml) documents `Authorization: <API-key>` and read-only `POST /events/restSearch`. The [self-user endpoint](https://github.com/MISP/MISP/blob/7dce1ef58bc16f0249ea4b53b2a29585645145a3/app/Controller/UsersController.php) resolves `/users/view/me` to the authenticated account. Restricted key endpoint allowlists must permit both self-read and event search. No write/publish/sync-user permission is required.

Background snapshots recheck native identity before paginated searches. Requests use ten-event full JSON pages, `withAttachments=false`, `excludeLocalTags=false`, `deleted=false`, verified TLS, no redirects, bounded responses and a 30-second read budget plus a possible in-flight socket wait. Pilot bounds remain 500 events/20 MB total and 2 MB per response. Oversized/partial/malformed/repeated pages fail visibly without publishing a partial result. Complete local merges are atomic and source-locked, preserving UUID/remote-ID/timestamp/digest and nested evidence. Failures preserve previous data but suspend reads; missing events stay stored and unavailable. In-flight source generations, credentials, endpoint approval and current ownership/membership are checked again before publication. No inventory, company name or contact is uploaded to MISP.

Defaults are a five-minute refresh and ten-minute maximum cache age (operator configurable up to sixty). Native permission revocation therefore has a bounded delay until refresh/expiry, not instantaneous per-request upstream enforcement. Navigation never calls MISP or renews stale permission evidence. This is a read cache, not native MISP replication or a strong upstream snapshot. Large-corpus manifests/deltas/checkpoints remain future work.

Local CSRF-protected research checks at most 100 attributes, 2,000 visible verified claims and 100 output leads, with explicit incompleteness. It supports public individual IPs, domains/hostnames and domain|IP values using address arithmetic/DNS label boundaries. For a customer connection it can only match that company. Private/unverified assignments, historical attribution and software/version matching are not implemented. Matches are leads, not compromise/affectedness proof; no finding, risk score, notification or upstream sighting is created.

## CIRCL investigation stays separate

A CIRCL analyst may retain an internal connection using their own broad MISP rights, managed with `python3 scripts/dev.py configure-misp --owner ANALYST --misp-user-id NATIVE_ID`. This environment-secret installer is for staff investigation, not customer onboarding, and refuses customer owners. A CIRCL cache is never a customer cache or fallback. A platform account has no blanket event-reading bypass. Old manual reader grants do not authorize access; migration 0039 quarantined previous shared-key caches rather than transferring them.

Even when CIRCL can read every event, forwarding content or derived notices to a company remains a separate recipient/handling decision. No TLP:RED content enters company dashboards, maps or notifications just because CIRCL can see it. Customer reads here are their own authorized upstream access, not redistribution of CIRCL's data.

See [customer guide](../user-guide/personal-misp.md) and [validation](../validation.md). Actual private-service version/key/native distribution acceptance, production retention/recovery and large-corpus synchronization remain open. No live MISP write, production notification, native user creation or public deployment was performed.
