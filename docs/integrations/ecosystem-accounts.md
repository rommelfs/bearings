# Ecosystem accounts and intelligence integration proposal

Status: **design proposal**, researched 2026-11-19. Existing public Vulnerability-Lookup reads/product discovery and explicit Bearings/NetBox SSO are implemented separately. No authenticated Vulnerability-Lookup community action, external account provisioning or production service modification is enabled by this proposal. A subsequent [bounded restricted MISP cache pilot](misp.md) now implements configurable read-only searches and local current verified IP/domain assignment leads; broader correlation, redistribution and feedback below remain future work. The cache now binds a separate personal key/native MISP user ID to each analyst; shared-key reader grants were removed. No supplied API key was requested, used or stored during research.

## One company-facing workspace

Bearings should remain the responsible person's everyday interface: maintain inventory, follow relevant vulnerabilities, review evidence, keep contacts current and acknowledge notices. Most companies need neither a second Vulnerability-Lookup account nor a native MISP account to do this. Keep company-specific subscriptions and remediation status local to Bearings; they expose installed technology and operational state.

Use separate native application access for people who need it, through a shared approved IdP, explicit account enrollment and application-specific roles. An API key authorizes machine requests as its issuing account; it does not establish a browser SSO session or automatically represent each Bearings user. A CIRCL service credential must not make every company action appear to be a personal CIRCL statement. If personal upstream contributions become necessary, design explicit delegated/personal credential attribution and revocation first.

## Vulnerability-Lookup

Upstream inspected at [21adb22c](https://github.com/vulnerability-lookup/vulnerability-lookup/tree/21adb22c5a1aa2103429eb11650819ea95decf26). Its [SSO documentation](https://github.com/vulnerability-lookup/vulnerability-lookup/blob/21adb22c5a1aa2103429eb11650819ea95decf26/docs/sso.md) describes OIDC authorization-code/PKCE, a separate client, pre-existing active/confirmed accounts, verified-email matching and optional required claims. It does **not** use Bearings' explicit issuer/subject linking rule. A trusted broker must prevent company identity providers from asserting other companies' addresses. Account activation, reassigned email addresses, MFA and revocation need acceptance on the selected deployed version. The public vulnerability.circl.lu deployment's enabled SSO/provider configuration has not been verified.

Proposed increments:

1. Enrich the existing CVE/product view with source-linked public comments, bundles and sightings, preserving provenance, revision/freshness and independent evidence. Deduplicate origins already received through MISP or other feeds. More mentions are not automatically more independent evidence.
2. Keep tailored watches and company remediation confirmations inside Bearings. Reuse upstream information while avoiding duplicated user configuration or disclosure of company inventory.
3. Offer an explicit reviewed contribution draft for a useful public comment, bundle or correctly typed sighting. Preview destination, author/account, payload and intended visibility before any write. Installed vulnerable software is not evidence of exploitation; a patch acknowledgment is not an exploitation sighting. Default to no external publication of company names, addresses, IPs, software versions or patch status.
4. Native SSO for authorized contributors is a separate deployment task. Provision the approved provider client and existing upstream account; do not sync passwords or treat a service API key as a user's login.

The inspected [comment](https://github.com/vulnerability-lookup/vulnerability-lookup/blob/21adb22c5a1aa2103429eb11650819ea95decf26/website/web/api/v1/comment.py), [bundle](https://github.com/vulnerability-lookup/vulnerability-lookup/blob/21adb22c5a1aa2103429eb11650819ea95decf26/website/web/api/v1/bundle.py) and [sighting](https://github.com/vulnerability-lookup/vulnerability-lookup/blob/21adb22c5a1aa2103429eb11650819ea95decf26/website/web/api/v1/sighting.py) APIs expose public reads and permission-checked writes. Actual account capabilities, moderation and deployed schemas remain to be validated. The [user API](https://github.com/vulnerability-lookup/vulnerability-lookup/blob/21adb22c5a1aa2103429eb11650819ea95decf26/website/web/api/v1/user.py) includes authenticated `/user/me`; its user representation includes an API-key field. Any future connection probe must whitelist safe status fields and must never log/store the full response or rotate the key as a connectivity check.

## MISP

Upstream OIDC documentation inspected at [7dce1ef5](https://github.com/MISP/MISP/blob/7dce1ef58bc16f0249ea4b53b2a29585645145a3/app/Plugin/OidcAuth/README.md). The plugin supports a configured provider/client and optional mixed local/OIDC login. Its role/organization mapping and account lifecycle require explicit review; do not copy example default organizations or auto-assign company users to CIRCL. The documentation also distinguishes blocking IdP login from disabling existing API keys/email. Neither native MISP SSO nor automatic provisioning is installed in Bearings by this change.

Recommended first integration is **CIRCL-only read/search and reviewed correlation**:

- Map approved company references to MISP organization UUIDs, using the newly implemented platform-attested optional reference. `Org`/`Orgc` identifies event organization/creator context; it does not establish that the organization is the victim or owns every indicator. Never infer responsibility from a display name, creator UUID or email alone.
- Read selected authorized events/attributes/objects with pagination, provenance, markings, event/object relationships, observation times and incremental checkpoints. The [existing MISP boundary](misp.md) remains the minimum contract. Avoid synchronous upstream work in National Overview; background ingestion and bounded local queries keep navigation independent of remote latency.
- Correlate victim/target infrastructure with currently or historically verified company IP/range/domain responsibility. Use address arithmetic and DNS label boundaries, preserve uncertain/ambiguous matches and distinguish malicious infrastructure from targeted infrastructure. A matching malicious IP in a company's netblock is a research lead, not proof the company is compromised.
- Match explicit vulnerability/software/version facts to inventory, including no-CVE intelligence where structured evidence permits. Record affectedness uncertainty; a keyword or CVE mention alone does not establish an affected asset.
- Show CIRCL an explained queue: source event, candidate company/asset, match reason, timestamp, confidence/uncertainty and contact. An analyst chooses whether and what to notify using existing Bearings draft/review workflows.
- Enforce distribution, sharing groups, event/attribute restrictions, TLP and operator policy on both raw and derived information. TLP:RED information must not enter general company dashboards, national counts, maps or outbound notices merely because a service key can read it. An authorized recipient set and handling decision are required; unknown eligibility remains restricted.

Later, separately approved increments can return a reviewed sighting/analyst feedback or create a draft MISP event with a pinned source reference. No automatic inventory/contact upload, blanket sharing-group assignment, event publication or compromise declaration is proposed. Imported and outbound origins need deduplication and lost-ack recovery to prevent circular evidence and duplicate writes.

## Operator configuration and acceptance

Use independent server-side credentials per service/instance and purpose. Begin with the least-privilege reading account; a personal all-powerful key is not a deployment architecture. Inject keys through private runtime secret references, never applicant forms, browser local storage, Git or chat. Keep approved fixed HTTPS destinations, TLS verification, bounded responses/timeouts, no redirects, scrubbed errors and current authorization checks. A cached key/account probe is not proof of every API permission.

Before a live pilot, establish the exact MISP base URL/version, Vulnerability-Lookup deployment/version, key account/capabilities, approved data scope/recipient rules and whether the operators can configure the shared IdP. First validate read-only capability/status responses without printing secrets or restricted content. Upstream writes, user creation and production notification require a separate concrete reviewed action. These details are not needed to evaluate the proposal and have not been assumed.

Suggested sequence: MISP CIRCL read/search with restricted correlation → richer Vulnerability-Lookup evidence in Bearings → native SSO for selected contributors → explicitly reviewed upstream feedback. This gives company users one useful interface before adding account synchronization machinery.
