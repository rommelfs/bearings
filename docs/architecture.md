# Architecture and current boundaries

Bearings is a Django modular monolith with a relational database (PostgreSQL target, SQLite local fallback), server-rendered interface, and session-authenticated `/api/v1/` read API. It consumes upstream services rather than modifying them. [ADR 0001](decisions/0001-modular-monolith.md) records the stack decision.

`portal/models.py` holds the initial domain; `access.py` centralizes policy; `scope.py` implements pure address/domain rules; `services.py` owns domain transactions; `connectors/` contains thin HTTP adapters; `views.py` scopes every request before loading objects. Templates render escaped data. These modules can become separate Django apps when boundaries warrant it; no microservices, search cluster, or graph database is introduced.

An organization has exactly one source binding. In central mode NetBox owns infrastructure; local assets are unconfirmed submissions or last-known projections. Software installations, claims, contact reviews, findings, and workflows belong to Bearings. Source binding UUID, object type, and external ID identify imported objects; IPs are not identities. Each binding selects an operator-managed NetBoxInstance. Shared instances require a tenant mapping; whole-instance access requires explicit dedicated ownership. Tenant assignment does not grant application access.

The development source is an explicit fixture backend. It records synthetic external IDs and must never be presented as successful NetBox integration. Organization-owned NetBox connections can now be queried with explicit per-instance read-only/read-write capabilities; common-model import is implemented; do not duplicate its inventory into central NetBox or introduce bidirectional sync.

`InventoryWrite` is the durable background-job/outbox entry. PostgreSQL row locking serializes a job across workers; retries use capped backoff. `process_jobs` executes at most 100 due items per invocation. Production scheduling is not included. The reminder command locks each organization and deduplicates by contact and review due date. Network outages retain all local data. The GET-only importer serializes on the same source row before projecting a complete snapshot; a savepoint rolls back all projection changes on failure while retaining the source lock for accurate health. Missing objects are retained for review, never deleted.

Operator-owned settings are server environment and platform administration: visibility policies, membership/source bindings, tenant mapping, connector URLs/tokens, review interval, database, and future delivery policy. Organization forms cannot modify these. File-mail delivery is deliberately fixed in code until operational messaging is authorized.

Production outbound requests require an operator egress allowlist in addition to application checks. URLs are HTTPS, operator-configured, disallow embedded credentials and redirects, and reject non-global DNS results unless NetBox private access is explicitly approved. DNS validation alone does not prevent DNS rebinding; upstream names must be controlled and deployment egress restrictions enforced. Organization-supplied connectors are blocked until stronger approval controls exist.

Cloud proxy-only DNS is explicitly opt-in through `CONNECTOR_PROXY_DNS=1`, requires an existing HTTPS proxy and an exact `CONNECTOR_ALLOWED_HOSTS` match, and delegates destination DNS/policy enforcement to that approved proxy. Private IP literals remain blocked unless explicitly approved for NetBox. This avoids unsupported direct DNS in the cloud without weakening TLS or exposing caller-controlled destinations. Direct-network mode retains DNS/address checks.

NetBoxInstance separates endpoint identity, credential reference, authentication scheme and read/write capability from the organization binding. Credentials remain outside the database. The GET-only query runner spans selected/all live bindings and validates every page and returned tenant; it records query health separately and makes no local inventory changes. Read-only/disabled capabilities are enforced at both submission and connector/job boundaries. See ADR 0003 and the integration document.

The optional starter composes Bearings with official NetBox, separate PostgreSQL storage, Valkey and a local HTTPS gateway. One-off initializers own local synthetic provisioning and generated secrets; live processes start only afterward. External mode runs no bundled NetBox services and performs no remote writes during bootstrap. Its dedicated development workspace defaults to denied analyst visibility. The fixed seed projection is distinct from the general importer run periodically by the worker. Source import health is separate from query health and write acknowledgement.

Inventory pages contain 50 assets; the read API returns 100 per page with pagination metadata. Upstream-owned name and an allowlisted metadata projection refresh independently of local kind refinements, criticality, lifecycle, team, software and findings. A source-local confirmed bearings_id may reconcile a pending create before a retry. Network objects never automatically establish ownership claims or source-to-source synchronization. See ADR 0005.
