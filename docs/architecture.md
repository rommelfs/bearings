# Architecture and current boundaries

Bearings is a Django modular monolith with a relational database (PostgreSQL target, SQLite local fallback), server-rendered interface, and session-authenticated `/api/v1/` read API. It consumes upstream services and has separate explicitly approved write paths for configured NetBox inventory and case/ticket hand-offs. [ADR 0001](decisions/0001-modular-monolith.md) records the stack decision.

`portal/models.py` holds the initial domain; `access.py` centralizes policy; `scope.py` implements pure address/domain rules; `services.py` owns domain transactions; `connectors/` contains thin HTTP adapters; `views.py` scopes every request before loading objects. Templates render escaped data. These modules can become separate Django apps when boundaries warrant it; no microservices, search cluster, or graph database is introduced.

An organization has exactly one source binding. In central mode NetBox owns infrastructure; local assets are unconfirmed submissions or last-known projections. Software installations, claims, contact reviews, findings, and workflows belong to Bearings. Source binding UUID, object type, and external ID identify imported objects; IPs are not identities. Each binding selects an operator-managed NetBoxInstance. Shared instances require a tenant mapping; whole-instance access requires explicit dedicated ownership. Tenant assignment does not grant application access.

The development source is an explicit fixture backend. It records synthetic external IDs and must never be presented as successful NetBox integration. Organization-owned NetBox connections can now be queried with explicit per-instance read-only/read-write capabilities; common-model import is implemented; do not duplicate its inventory into central NetBox or introduce bidirectional sync.

`InventoryWrite` is the durable background-job/outbox entry. PostgreSQL row locking serializes a job across workers; retries use capped backoff. `process_jobs` executes at most 100 due items per invocation. Production scheduling is not included. The reminder command locks each organization and deduplicates by contact and review due date. Network outages retain all local data. The GET-only importer serializes on the same source row before projecting a complete snapshot; a savepoint rolls back all projection changes on failure while retaining the source lock for accurate health. Missing objects are retained for review, never deleted.

Platform operators control visibility/source bindings, tenant mapping, connector destinations/capabilities, review intervals, database and transport settings. Company administrators can manage their own membership invitations/roles; this cannot grant platform/CIRCL/native roles. Optional customer MISP keys are encrypted, owner/company-bound and accepted only at operator-approved destinations. Development mail defaults to a local file sink; optional SMTP and reviewed outreach retain separate delivery/response evidence and require operational acceptance.

Production outbound requests require an operator egress allowlist in addition to application checks. URLs are HTTPS, operator-configured, disallow embedded credentials and redirects, and reject non-global DNS results unless NetBox private access is explicitly approved. DNS validation alone does not prevent DNS rebinding; upstream names must be controlled and deployment egress restrictions enforced. Organization-supplied connectors are blocked until stronger approval controls exist.

Cloud proxy-only DNS is explicitly opt-in through `CONNECTOR_PROXY_DNS=1`, requires an existing HTTPS proxy and an exact `CONNECTOR_ALLOWED_HOSTS` match, and delegates destination DNS/policy enforcement to that approved proxy. Private IP literals remain blocked unless explicitly approved for NetBox. This avoids unsupported direct DNS in the cloud without weakening TLS or exposing caller-controlled destinations. Direct-network mode retains DNS/address checks.

NetBoxInstance separates endpoint identity, credential reference, authentication scheme and read/write capability from the organization binding. NetBox operator credentials remain outside the database. Optional personal MISP credentials use separate encrypted storage, described in the MISP contract. The GET-only query runner spans selected/all live bindings and validates every page and returned tenant; it records query health separately and makes no local inventory changes. Read-only/disabled capabilities are enforced at both submission and connector/job boundaries. See ADR 0003 and the integration document.

The optional starter composes Bearings with official NetBox, separate PostgreSQL storage, Valkey and a local HTTPS gateway. One-off initializers own local synthetic provisioning and generated secrets; live processes start only afterward. External mode runs no bundled NetBox services and performs no remote writes during bootstrap. Its dedicated development workspace defaults to denied analyst visibility. The fixed seed projection is distinct from the general importer run periodically by the worker. Source import health is separate from query health and write acknowledgement.

Inventory pages contain 50 assets; the read API returns 100 per page with pagination metadata. Upstream-owned name and an allowlisted metadata projection refresh independently of local kind refinements, criticality, lifecycle, team, software and findings. A source-local confirmed bearings_id may reconcile a pending create before a retry. Network objects never automatically establish ownership claims or source-to-source synchronization. See ADR 0005.

## Optional FlowIntel boundary

The [FlowIntel pilot](user-guide/flowintel.md) runs as a separate application/database. Bearings owns scoped evidence, applicability and notification approval; FlowIntel owns private CIRCL case/task workflow. A reviewed immutable snapshot and four tasks cross the API boundary only after approval. Server-side instance credentials, committed write claims, exact case identity/privacy checks and bounded read-only reconciliation constrain hand-off. Read-back status is separate from remediation; completing a case never changes a finding, NetBox or a company message. Customer accounts are not provisioned in FlowIntel.


## National read models at large inventory sizes

PostgreSQL installations with more than 100 currently visible companies use disposable per-company national projections. `NationalState` carries the freshness/invalidation marker, coverage totals and two evidence audiences; version, exact product/version, problem and daily activity rows remain scoped by company. Current organization visibility, membership and evidence audience are applied when serving every request. There is no globally shared privileged dashboard response cache. Company pages and small/SQLite scopes retain live queries.

Database statement triggers invalidate affected companies in the same transaction as relevant inventory/evidence changes, including bulk SQL. Routine health timestamps do not invalidate inventory aggregates. A dedicated `national-worker` service refreshes bounded batches independently of external imports. State row locking and writer serialization prevent a committed change from being marked clean accidentally. Pending companies are disclosed as incomplete coverage in national panels; no prepared data produces a retryable unavailable response. Map/research reads can combine clean projections and at most 1000 pending companies from live data inside one repeatable-read transaction; larger pending sets use bounded live fallback. This preserves exact research results during updates.

Global company cards, selectors, audit work and hydrated review/issue pages are bounded before related records load. Ordering/eligibility is evaluated on narrow primary keys and full authorization is reapplied when hydrating. Correlated same-company checks remain in SQL; their query form avoids independent-column selectivity guesses that selected catastrophic nested loops. Map, lists and confidential research have private recoverable overload responses. See [measurements and operating procedure](performance/scale-improvements.md).
